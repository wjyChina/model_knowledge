MiniMax H3：统一文本、图像、视频、音频条件的音视频生成

H3 的独特点不是单纯把 T2V 的输入再加一个音频接口，而是把多种模态放进一条统一的 packed 生成路径：文本走 H3-Encoder（完整预训练的 Qwen3-VL-32B，取第 50 层 hidden states），视觉走 H3-VisualVAE （f16t4d24：空间 16×、时间 4×、24 通道，再按 1×2×2 patch 化，token 有效空间下采样 32×），音频走 H3-AudioVAE（32 kHz 立体声、每通道 40 Hz latent）；主干 H3-Omni-Transformer 是 33B dense single-stream，其中约 13B 参数在 AdaLN 分支（调制输出可预计算缓存，仅推理部署 不必加载），位置编码使用 MM-RoPE (t,h,w)。本页只写公开资料确证的内容；层数、 hidden size、loss 形式、solver 名称与步数一律标为需要核验。

1. H3 的独有定位：一个统一的多模态音视频模型

对普通 T2V 模型，可以把输入简化成“文本条件 + 随机视频 latent”。H3 的公开任务范围更宽： 文本、图像、视频和音频都可以成为条件，模型也可以生成带同步音频的音视频结果。 这意味着“参考图”“已有片段”“声音节奏”不必先被人工改写成一段文字再进入模型，而可以保留为各自的模态条件。

阅读边界（已确证 / 未公开）：官方公告明确给出三个模块的分工 （H3-Context-IR → H3-Base → H3-Regenerate-2K）、两种编码器与一种 VAE 的压缩率、主干规模 33B dense 与约 13B 的 AdaLN 参数占比、MM-RoPE 的三维坐标形式，以及“首个开源版本只提供全注意力推理”。 但官方没有给出主干层数、hidden size、训练损失形式、solver 名称与默认步数，也没有公开各模态 token 在 packed 序列中的拼接顺序。本页与结构图不会把未公开的部分补成看起来合理的细节： 看到具体权重时，请按 transformer/config.json、推理脚本与 named_modules() 逐条核对。

3. H3-Omni-Transformer：视频和音频为什么可以一起预测

传统管线常见做法是先生成视频，再单独配音，最后把两个文件 mux 到一起；这样声音和动作 只能在后期对齐。H3 的公开描述把视频 latent 与音频 latent 放进同一个联合生成系统：主干在同一次条件推理中读取 packed 多模态上下文，并产生两种 latent 的预测结果。官方还明确了一个容易被画错的细节：attention 与 FFN 都不含模态专属结构，模态专属参数只在输入/输出层与 AdaLN 分支，因此“视频分支”和“音频分支”不是两套独立的 Transformer 主干。 这样“说话时张嘴”“鼓点对应运动”等关系有机会在生成阶段建立，但最终质量仍取决于 checkpoint、条件与解码器，联合主干不等于自动保证完美同步。

4. 不同任务怎样改变输入

任务名描述的是条件组合，不代表每个 H3 checkpoint 都自动支持全部组合。使用前看模型卡和推理脚本的实际参数。

T2V输入 prompt；video/audio 初始状态来自随机 latent，主干生成一段带声音的视频。 I2V加入一张图作为外观/首帧/参考条件；图像信息在条件路径中持续提供给主干。 V2V / 续写加入源视频或尾部上下文；源内容先编码，再作为 latent 或视觉条件参与更新。 音频到音视频加入 waveform、mel 或音频 latent；声音节奏成为联合主干的条件，输出仍需检查音画同步。 参考到音视频文本、图像、视频、音频可以组成参考集合；实际可用的组合以 checkpoint/API 说明为准。

5. “多步生成”时，额外信息是第一次输入还是每一步输入？

对 H3 这类迭代式 latent 生成，必须区分“固定条件”和“会变化的生成状态”。下面用变量写出每一步的关系，避免把参考图误解成只在第一步拼接一次。

变量 第一次准备 每个 step 的使用 是否更新
c_text / c_image / c_video / c_audio 由各自 encoder 计算 作为条件再次送入主干的 cross/joint 条件路径 通常固定；除非实现有逐步 guidance 或窗口更新
z_video(t), z_audio(t) 随机或由源内容初始化 当前 step 的 noisy latent 输入 每一步都会更新为下一时间点
t 由采样器建立时间序列 告诉主干当前噪声/流状态 每一步变化
mask / reference window 从输入视频或编辑区域计算 按实现广播到对应的空间、时间或 token 位置 内容可能固定，窗口索引可能随 chunk 变化
一句话：参考图、文本和音频特征通常是“先编码、每步读取的固定条件”；视频/音频 latent 和时间步 t 是“每步都会变化的状态”。最终以 H3 推理代码的 forward 签名和 scheduler/solver 实现为准。

6. H3 微调：先确认联合主干的真实模块名

不要因为页面写了 “Transformer” 就直接把 LoRA 挂到所有线性层。先下载目标 checkpoint，读取 config 和权重，再打印真实模块树。 对 H3 这类联合音视频模型，候选位置至少要分成视频路径、音频路径、两者共享的 attention/MLP、条件投影和输出头； 如果只训练视频风格，就要确认是否误更新了音频分支或跨模态对齐层。

H3 的训练数据和两种微调路线

H3 数据不能只保留一个 MP4。每条样本应保存视频、音频、文本描述、FPS、帧数、分辨率、音频采样率、时长、音画偏移、参考图/参考视频和授权信息；按作品或主体切分 train/validation/test，保证验证集没有同一镜头的相邻片段。音视频联合数据还要抽查口型、鼓点、动作与声音是否真的对齐。

需求 数据形式 建议训练 验收
视频风格/镜头 video + caption + motion/camera 标签，可选参考图 先只挂 video branch LoRA；冻结 audio/shared 分支 动作、身份、镜头、闪烁和文本遵循
声音/口型 video + aligned audio + transcript/phoneme + offset 训练 audio branch 或 audio-video cross projection；不要误调全部主干 音画同步、口型、节奏、语音清晰度
联合音视频 video、audio、caption、参考条件、时长/FPS/采样率 确认 shared block 与两个输出头后再做联合 LoRA；小数据先低 rank 跨模态条件遵循、画面与声音联合盲评

如果只训练视频风格，目标仍是对 noisy video latent 的 epsilon/velocity loss；如果训练音频或联合路径，则同时计算 audio latent 的目标，并按照实现对 shared/output head 加权。先用少帧、低分辨率和短时长跑通 forward/backward，再扩展时长。发布前固定模型 revision、模块清单、LoRA rank/alpha、冻结范围、音频采样率和同步回归集；公开资料没有说明的 H3 loss 或 solver 不应自行写成确定事实。

7. 能确认什么，仍要查什么

公开资料可以确认（官方公告 / 模型卡） 仍无法确认，必须按 checkpoint 核验
H3 由 H3-Context-IR、H3-Base、H3-Regenerate-2K 三个模块组成；其中只有 H3-Base 开源，另外两个只在 API 提供。 主干层数、hidden size、head 数；以及各版本之间的差异（读 transformer/config.json）。
H3-Encoder 使用完整预训练的 Qwen3-VL-32B，取第 50 层 hidden states；tokenizer 增加了 <d> 等特殊 token。 第 50 层之后的部分如何使用、条件 token 如何投影到主干宽度（公开说明未给出）。
H3-VisualVAE = f16t4d24（空间 16×、时间 4×、24 通道），latent 再按 1×2×2 patch 化 → token 有效空间 32×、时间 4×；H3-AudioVAE = 32 kHz / 每通道 40 Hz。 latent 的具体张量布局、初始化的加噪公式与 sigma 序列。
H3-Omni-Transformer = 33B dense single-stream，约 13B 参数在 AdaLN 分支且调制输出可预计算缓存；attention/FFN 无模态专属结构。 训练损失形式、时间采样分布、guidance/CFG 蒸馏做法、solver 名称与默认步数。
发布的是两个 CFG-distilled checkpoint（FL2VA、Ref2VA）；输出 768p、24 FPS、4–15 秒、32 kHz 立体声；输入上限为 ≤9 图 / ≤3 视频 / ≤3 音频 / 合计 ≤12 文件，且音频不能单独作为输入。 本地硬件能否达到 2K 与 15 秒边界；2K 需要闭源的 H3-Regenerate-2K； 稀疏注意力实现尚未发布。
